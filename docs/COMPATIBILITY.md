# 兼容范围

## 基线

以发布版 Rust `filecheck=0.5.0` 为行为对照，差分适配器固定 `regex=1.11.1`，依赖细节锁定在 `reference/oracle/Cargo.lock`。这与 LLVM 的 `CHECK` / `CHECK-DAG` 语法不是同一套协议，不能直接替换 LLVM FileCheck。

本项目实现 `check`、`sameln`、`nextln`、`unordered`、`not` 和 `regex`，包括变量捕获、引用、正则变量、空模式、字面量美元符号和正向匹配屏障。`unordered` 可重叠；涉及捕获变量时，下界受定义位置限制。不存在自动搜索所有排列的回溯求解。

## 已验证

- 上游 `tests/basic.rs` 提取的 48 项结果。
- 项目固定语料，以及固定种子生成的 2400 组组合。
- Unicode 中英文、补充平面字符、CRLF、零长度匹配、冻结否定变量值、正则命名捕获。
- `not:` 的起止范围、尾部否定、无序屏障和无序变量依赖。

通过该语料不代表所有 Rust 正则表达式或所有输入已证明等价。

## 正则表达式

使用固定的 `moonbitlang/regexp 0.3.7` 源码并带有记录在 THIRD_PARTY.md 的本地修复。常用字面量、分组、选择、字符类、量词、`\b`、命名捕获以及 Unicode general category 可用。`(?P<name>...)` 被翻译为该引擎的 `(?<name>...)`。

不支持回溯引用、look-around、Rust regex 的全部 inline flags、字符集运算以及 `\A` / `\z` 等扩展。显式禁用反向引用，避免启用依赖库的指数回溯路径。某些表达式即使被引擎接受，其语义也未覆盖：例如 `\d` 为依赖库的 ASCII 数字语义，`\s` 使用其 ECMAScript 风格空白集合，不能假定与 Rust Unicode 语义等价。跨实现可移植的数字/空白规则请使用 `[0-9]`、`[ \t\r\n]` 等明确字符类。

`\w` 和单词边界使用 Rust regex 1.11.1 的 Unicode 16.0.0 单词字符表。自动添加边界的条件根据首末字面量是否属于 Unicode general category L/N；Rust `char::is_alphanumeric` 的少数 Other_Alphabetic 字符不在这一条件中，尚未实现完全等价。诊断列是标量计数，不是 grapheme/display width。

## 有意的接口差异

- CLI/JSON 默认拒绝空规则；库保留空 Checker 可以通过的行为。
- 正则定义在解析时预检查。未使用的非法 `regex:` 也会报错；上游可在运行到引用时才发现。
- 每个指令需在同一行，冒号后使用水平空白，不支持通过 `\s+` 跨行延续指令。
- 加入输入、规则和表达式长度上限；CLI 还有 Worker 运行时间与堆内存限制。
- 诊断措辞与 Rust 不相同；只比较成功、失败、错误三类状态，不声称诊断文本逐字兼容。
- 捕获名不能以数字开头，与实际 Rust named capture 的限制一致；外部变量名和引用仍可使用数字。

## 资源与平台

CLI 文件/标准输入上限 16 MiB，UTF-8 解码严格；核心输入上限 8,388,608 个 UTF-16 code unit，规则文本上限 1,048,576，模式上限 4096，展开的正则上限 8192，指令最多 10000 条。

0.1.1 增加：外部变量最多 10000 个，名字最多 4096、值最多 8192 个 UTF-16 单元；展开预算为两侧可选单词边界预留 4 单元。分组深度最多 64、分支分隔符最多 256；编译成本保守上限 100000，超限表达式提前拒绝。JSON 数组必须含 1..4096 项，evaluate API 的序列化请求也限制为 16 MiB。以上限制属于有意的兼容差异。

CLI 默认 30 秒引擎超时，`--timeout` 可设为 1..300000 毫秒，Worker 堆上限 256 MiB。纯库 API 没有宿主 Worker 隔离，处理不受信任的复杂规则时应由调用方设置资源边界。这些限制不构成完整的正则执行成本模型。

核心测试覆盖 JS、wasm-gc、native。JS/Node CLI 在当前 Windows 环境验证；Linux/macOS 的工作流已提供，尚无远端 CI 执行记录。原生独立 CLI 可作为后续扩展，当前没有承诺其已实现。
